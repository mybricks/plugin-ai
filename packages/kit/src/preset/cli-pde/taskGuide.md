<文档维护>
在 `.lingchuang` 文件夹下，总共有三类文档，每一个文档有一个单独的视图：

1. 任务视图：又称任务文档，分析当前分支已提交和未提交的内容，生成可理解的任务列表，用于管理和理解当前分支迭代的内容。
迭代时机：每一轮涉及代码修改任务都应该自我迭代，注意是代码修改内容，文档自身的迭代不算；
相关文件：`TASKS.md`
包含内容：按照任务拆分代码修改的内容。
不应该包含的内容：.lingchuang 文档本身的迭代，比如审计视图的更新，不属于代码修改任务。

2. 影响视图：又称影响文档，分析当前分支已提交和未提交的内容，通过通用规则和自定义规则，分析代码的影响范围，以确认是否有隐患或者未被发现的问题。
迭代时机：仅在用户主动提及或者修改 `影响文档`时迭代；
相关文件：`REVIEW.md`

3. 审计视图：又称审计文档、可视化文档，主要是分析某个页面的接口、事件和状态，生成可审计的可视化文档。
迭代时机：仅在用户主动提及或者修改 `审计文档` 时迭代，提及接口、事件和状态的可视化信息时也要迭代，迭代时先使用了解 `audit-power` 技能；
相关文件：`.lingchuang/graph/*.yaml`

三类视图的关系：
1. 任务视图，位于页面左下角「任务」面板
2. 影响视图，位于页面左下角「影响」面板
3. 审计视图，直接将可视化内容展示到页面浮层上，绿色为状态、黄色为事件。

其中任务视图和影响视图的内容不应该重叠。

> 注意：任何文档的内容，都不应该包含文档自身的更新，如 `更新了审计文档` 这种内容。

<TASKS.md>

TASKS.md 是当前分支所有开发工作的唯一事实来源。你不是在写完代码后补一份记录，而是先明确任务、再动手写代码、最后回写进展，让用户能清晰地看到「做了什么、还剩什么、哪些卡住了需要交给别人」。任何一轮涉及源码改动的对话，都必须落到某一条任务上。

## 文档位置

`.lingchuang/<分支名>/tasks/TASKS.md`，**按当前 Git 分支名命名文件夹**，最终文件名固定为 `TASKS.md`，一个分支对应一份报告。分支名应转换成 字母+数字+下划线 三类字符；例如 `feat/add-card` 对应 `.lingchuang/feat_add_card/tasks/TASKS.md`。

## 任务生命周期

### 每轮对话的三个动作

1. **开场读取**：动手改代码前，先读取本分支的 TASKS.md（文件不存在则视为空文档），了解已有任务及其状态。
2. **开发推进**：按常用工作流实现改动。
3. **收尾回写**：改完代码后立即更新 TASKS.md，然后才向用户汇报。

跳过第 1 步的典型后果：重复新增已经存在的任务、遗漏本该流转的状态、把用户的验证反馈误当成新需求。

### 开场：任务归属判定

读完 TASKS.md 后，先判断本轮用户消息属于哪一类，再决定如何动手：

| 判定 | 特征 | 动作 |
| --- | --- | --- |
| 验证反馈 | 用户对上一轮结果表达肯定或否定，如「可以了」「不对」「还是有问题」 | 不新增任务，按「用户验证反馈的处理」流转已有的待验证任务 |
| 推进已有任务 | 需求与某条已有任务属于同一功能点，或是对它的修正、补充 | 更新那条任务，不新增 |
| 新任务 | 与现有任务无关的新需求 | 新增一条任务 |
| 与任务无关 | 纯提问、只读代码、只改 .lingchuang 文档自身 | 不改动 TASKS.md |

判不准时优先合并进已有任务，或直接询问用户，不要用「新增一条」来回避判断。

### 收尾：回写与汇报

只要本轮改动了源码，就必须回写 TASKS.md，无一例外：

- 仅改了一行样式、一处文案、一个颜色值，同样要回写；
- 改动量小、逻辑简单，都不是豁免理由；
- 唯一豁免是本轮零源码改动。

回写完成后，向用户的汇报中要包含 `任务名 → 状态`。

## 状态机

### 任务前期调研
核心是确认用户意图，判断任务是否可以闭环完成，对于不清楚的情况，务必和用户确认清楚方向。

比如在前端项目：
1. 可以确认的，用户明确的UI需求。
2. 无法确认的，用户的UI需求，需要服务端能力配合，但是你不清楚服务端代码。

### 状态与流转

按「本方代码写完没 → 能否闭环交付 → 用户确认没」三步分支，每一步只有两个去向：

```
                       ┌─ 能直接闭环 ──► 2.1 待验证 ──用户确认──► 3.1 已完成
1 处理中 ──写完代码──► ┤
                       └─ 依赖他方 ────► 2.2 待验证 ──用户确认──► 3.2 待交接
```

| 步骤 | 状态 | 进入条件 | 必填元信息 |
| --- | --- | --- | --- |
| 1 | 处理中 | 还在开发，没到能交给用户验证的程度；仅用于大任务中间态或被打断的情况 | 无，可选写验证进展 |
| 2.1 | 待验证 | 本方代码已落地，且可以直接闭环交付 | 验证进展 |
| 2.2 | 待验证 | 本方代码已落地，但依赖其他方确认或补齐能力（如依赖接口修改，接口实现尚未确定） | 验证进展、交接给、交接原因 |
| 3.1 | 已完成 | 2.1 经用户确认通过，整件事闭环 | 验证进展 |
| 3.2 | 待交接 | 2.2 经用户确认通过，余下需服务端等其他角色补齐才能整体生效 | 验证进展、交接给、交接原因 |

其中能否闭环交付是关键，比如你无法确定接口是否支持参数，请如实告知，比如新增UI，但不确定接口是否支持，不属于闭环，需要服务端确认。

如何处理用户反馈：
- 用户反馈有问题：停留在 2，在「验证进展」补充本次未通过的原因，修完继续等待确认。
- 用户表达肯定但有多条 *待验证* 无法确定指向：主动询问是哪一条，不要擅自全部标记完成。

### 进入终态的唯一路径

*待验证* 是进入任一终态的必经环节，*处理中* 不得直跳 *已完成* 或 *待交接*。唯一例外：改动对用户不可见（纯重构、类型修复、依赖升级、注释调整等）且构建或测试已通过，可直接写 *已完成*。

写入 *已完成* 前必须答得上来：谁验证的？证据是什么（用户原话或命令输出）？用户是否真的看到过这个效果？任何一问答不上来，就写 *待验证*。

严禁以「改动很简单、逻辑很直接、应该没问题、只改了两行代码、我已检查过没报错」为由直接写 *已完成*——编译通过只说明代码能跑起来，不说明效果符合用户预期。

### 判断示例

场景一：用户说「登录按钮改成蓝色」，你改了一行 CSS。
- 正确：任务状态写 *待验证*，验证进展写「请打开登录页，确认按钮已变为蓝色」。
- 错误：状态直接写 *已完成*，理由是改动很简单。

场景二：紧接上一轮，用户回复「可以了」。
- 正确：把那条任务转为 *已完成*，验证进展改写为「用户已手动验证通过，登录按钮显示为蓝色」。
- 错误：新增一条「登录按钮颜色调整」并标记 *已完成*，原来那条待验证任务留在文档里不动。

场景三：用户说「加个导出 Excel 的按钮」，导出需要服务端提供接口。
- 正确：前端完成按钮与交互后写 *待验证*，请用户确认按钮与交互；用户确认后转 *待交接*，「验证进展」写明按钮交互已验证通过、导出逻辑待服务端接口就绪，并填交接给服务端、交接原因是缺少导出接口。
- 错误：自行假定接口地址与参数，或跳过用户确认直接写 *待交接*。

场景四：你把组件里的重复逻辑抽成公共函数，页面表现无变化，构建通过。
- 正确：状态写 *已完成*，符合准入条件第 2 条。
- 错误：状态写 *待验证*，让用户去验证一个看不见的改动。

场景五：本轮只回答了用户「这个页面的数据从哪来」的提问，没改任何源码。
- 正确：不改动 TASKS.md。
- 错误：新增一条任务来记录这次问答。

## 任务标题与粒度

标题是跨轮匹配任务的依据，必须稳定、具体、可复用：

- 写「在哪个页面或模块做什么」，如 `登录页调整按钮样式`，而不是 `修改样式`；
- 同一功能点的后续修正沿用原标题，不要因为措辞变化就新开一条；
- 一条任务对应用户视角的一件事，不要按文件或按提交来拆分。

## 文档结构

每个任务由「二级标题 + 加粗列表元数据 + 一句话摘要」组成。

- **元数据**：用 `- **字段名**：值` 的形式列出，既能加粗展示，也能被程序按 `**字段**：内容` 稳定解析。
- **一句话摘要**：紧跟元数据的引用块（`>` 开头），一句话讲清这个任务是做什么的，让用户扫一眼就懂。摘要要有落点，说清「给谁/在哪个功能上做什么」，避免「优化了逻辑」这类空话。
- **摘要要「有落点、可追溯」**：具体到页面、模块或文件，写清做了什么、还差什么，而不是「调整了样式」「优化了逻辑」这类模糊描述。

## 元数据字段说明

字段取值使用固定枚举，便于解析。何时必填见状态机表，此处只规定写法：

| 字段 | 用途 | 取值 |
| --- | --- | --- |
| 状态 | 任务状态 | 处理中 / 待验证 / 待交接 / 已完成 |
| 交接给 | 交接接手方 | 角色 |
| 交接原因 | 为什么要交接出去 | 一句话说明，如缺少的接口/权限/信息 |
| 验证进展 | 当下能验到什么 | 待验证时写清用户该如何操作验证（打开哪个页面、点哪个按钮、观察什么结果，末尾提示验证通过后可告知你）；待交接、已完成时改写为验证结论，待交接还要写明哪部分要等他方就绪后才能验 |

字段名和取值严格按上表使用，不要自造，保证可被程序稳定解析。

```TASKS.md

- **状态**：处理中
- **验证进展**：报表页已能看到「导出」按钮，点击后暂无反应，导出逻辑还在开发中

> 在报表页新增「导出」按钮，把当前表格数据下载为 Excel。

## 编辑页新增上传头像能力

- **状态**：待交接
- **验证进展**：用户已确认，编辑页点击头像区域可选择本地图片并正常预览；保存后头像持续生效的部分，需服务端接口就绪后才能验证
- **交接给**：服务端
- **交接原因**：缺少上传与保存头像的接口能力，需要服务端设计提供

> 编辑页已完成头像上传的前端 UI 展示，具体上传与保存逻辑待接口设计实现后敲定。

## 登录页调整按钮样式

- **状态**：待验证
- **验证进展**：需要您打开登录页，确认登录按钮已变为品牌蓝、与输入框的间距变大，鼠标悬停时有背景渐变动画；如果符合预期，可以告知我已验证

> 在登录页把登录按钮改为品牌蓝，增大了按钮与输入框的间距，并添加了登录按钮的背景渐变动画，提升登录按钮的视觉效果。

## 列表页新增数据导出能力

- **状态**：待验证
- **验证进展**：请打开列表页，点击「导出」按钮，确认能弹出导出弹窗、勾选列后本地部分交互正常；确认后我再把状态转为待交接
- **交接给**：服务端
- **交接原因**：真实导出下载依赖服务端提供导出接口，前端无法独立完成

> 列表页已完成导出按钮与弹窗交互，等待用户确认前端交互后，交接服务端补齐导出接口。

## 列表页上传解析支持 csv 格式文件

- **状态**：已完成
- **验证进展**：用户已手动验证通过，上传 csv 文件后出现进度，表格自动刷新并展示 csv 文件内容

> 列表页新增上传 csv 文件解析功能，上传后自动解析并刷新表格展示。
```

## 维护规则

1. **每轮代码改动后必须维护**：先读取现有 TASKS.md，再依据用户需求、代码修改更新，除非本轮零源码改动。
2. **优先合并而非新增**：与已有任务相关的改动合并进那一条，不重复新增。
3. **摘要必写**：每个任务都要有一句话摘要，信息落在元数据和摘要里即可。
4. **状态按状态机流转**：不得绕过「已完成的准入条件」。
5. **粒度适中**：既不事无巨细，也不遗漏关键任务，核心是保障准确性和可维护性。
6. **有疑问就问**：若对任务归属或交接对象不确定，主动向用户确认意图。

## 收尾自检

回写完成后逐条确认，发现问题直接修，不必向用户复述检查过程：

1. 本轮的源码改动是否都落到了某条任务上？
2. 每条 *已完成* 是否都能说出验证证据（用户原话或命令输出）？
3. 每条 *待验证* 是否都写了「验证进展」？每条 *待交接*、*已完成* 是否都把「验证进展」写成了验证结论？
4. 是否新增了本该合并进已有任务的条目？
5. 字段名与取值是否严格取自元数据表？
6. 是否混入了文档自身的更新，如「更新了任务文档」？

</TASKS.md>

<REVIEW.md>
这一部分描述当前分支已提交和未提交的内容 造成的影响，需要结合修改内容判断。

### 输出位置

变更评估文档报告写入 `.lingchuang/<分支名>/reviews/REVIEW.md`，**按当前 Git 分支名命名文件夹**，最终文件名固定为 `REVIEW.md`，一个分支对应一份报告。分支名应转换成 字母+数字+下划线 三类字符；例如 `feat/add-card` 对应 `.lingchuang/feat_add_card/reviews/REVIEW.md`。

> 如果当前分支已经存在 Review 报告，直接修改文件即可。

### 报告结构

报告顶部是一个 YAML frontmatter，记录 `updateTime`（格式 `YYYY-MM-dd hh:mm`）。

正文由「一级标题 `# 影响列表` + 若干条评估规则」组成。每条规则是一个二级标题的评估维度，结构与任务文档保持一致：

- **二级标题**：规则名称，如 `影响范围`。
- **元数据**：紧跟标题，用 `- **字段名**：值` 的形式列出，既能加粗展示，也能被程序按 `**字段**：内容` 稳定解析。
- **一句话摘要**：紧跟元数据的引用块（`>` 开头），一句话讲清这条规则的评估结论。摘要要有落点，说清「哪个改动 / 涉及哪个功能 / 结论是什么」。
- **详细说明**（可选）：需要展开影响点、待确认项或修复建议时，在摘要下方补充自然段落。结论明确的简单规则只写摘要即可。

### 影响分析规则

- 内置规则：
1. 影响范围，我们面对的是非研发人员，他们无法确认自己的改动是否影响到了线上正在使用的功能，需要评估下当前修改的影响面；

- 自定义规则：
1. 目前暂无，不允许写

> 影响范围目前是必须实现的评估手段，后续可按需扩展新的评估维度（如「兼容性」「性能」等），未涉及的维度直接省略，不要留空标题。

```md
---
updateTime: 2026-09-01 15:30
---
# 影响列表

## 影响范围

- **状态**：需修复

> 千分位改动涉及公共函数 `format`，首页报表也引用了它，会被一并改成千分位展示，需确认首页是否符合预期。

`format` 位于 `utils/format.ts`，除列表页外还被首页报表 `HomeReport.tsx` 调用。导出等其余需求都限定在列表页，影响范围可控，仅首页报表这一处需要人工确认展示合理性。
```

### 元数据字段说明

每条规则的元数据字段固定枚举，便于解析：

| 字段 | 用途 | 取值 |
| --- | --- | --- |
| 状态 | 该维度的评估结论（必填） | 通过 / 需修复 / 严重问题 |

- **通过**：允许上线，无需处理。
- **需修复**：存在需人工确认或修复的点，修复后方可上线。
- **严重问题**：禁止上线，必须先解决。

## 特别注意

- 报告的阅读者是非研发人员，使用清晰具体的业务语言，避免未解释的技术术语。
- 不要为了审计而改动业务源码、需求文档或其他项目文件；只做分析与写审计报告。
- 字段名和状态取值严格按上表使用，不要自造，保证可被程序稳定解析。
