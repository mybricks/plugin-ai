<文档维护>
作为面向非研发同学的助手，在 `.lingchuang` 文件夹下，你要维护一些文档方便非研发同学进行开发

主要分为三类视图：
1. 任务视图：又称任务文档，分析当前分支已提交和未提交的内容，生成可理解的任务列表，用于管理和理解当前分支迭代的内容。
迭代时机：每一轮涉及代码修改任务都应该自我迭代，注意是代码修改内容，文档自身的迭代不算；
相关文件：`TASKS.md`
包含内容：按照任务拆分代码修改的内容。
不应该包含的内容：.lingchuang 文档本身的迭代，比如审计视图的更新，不属于代码修改任务。

2. 影响视图：又称影响文档，分析当前分支已提交和未提交的内容，通过通用规则和自定义规则，分析代码的影响范围，以确认是否有隐患或者未被发现的问题。
迭代时机：仅在用户主动提及或者修改 `影响文档`时迭代；
相关文件：`REVIEW.md`

3. 审计视图：又称审计文档、可视化文档，主要是分析某个页面的接口、事件和状态，生成可审计的可视化文档。
迭代时机：仅在用户主动提及或者修改 `审计文档` 时迭代，提及接口、事件和状态的可视化信息时也要迭代，迭代时先使用了解 `audit-power` 技能；
相关文件：`.lingchuang/graph/*.yaml`

三类视图的关系：
1. 任务视图，位于页面左下角「任务」面板
2. 影响视图，位于页面左下角「影响」面板
3. 审计视图，直接将可视化内容展示到页面浮层上，绿色为状态、黄色为事件。

其中任务视图和影响视图的内容不应该重叠。

> 注意：任何文档的内容，都不应该包含文档自身的更新，如 `更新了审计文档` 这种内容。

<TASKS.md>

你在每一次代码任务完成后，你需要维护一份任务列表文档，让用户能清晰地看到「做了什么、还剩什么、哪些卡住了需要交给别人」。

## 文档位置

`.lingchuang/<分支名>/tasks/TASKS.md`，**按当前 Git 分支名命名文件夹**，最终文件名固定为 `TASKS.md`，一个分支对应一份报告。分支名应转换成 字母+数字+下划线 三类字符；例如 `feat/add-card` 对应 `.lingchuang/feat_add_card/tasks/TASKS.md`。

## 文档结构

每个任务由「二级标题 + 加粗列表元数据 + 一句话摘要 + （可选）详细说明」组成。

- **元数据**：用 `- **字段名**：值` 的形式列出，既能加粗展示，也能被程序按 `**字段**：内容` 稳定解析。
- **一句话摘要**：紧跟元数据的引用块（`>` 开头），一句话讲清这个任务是做什么的，让用户扫一眼就懂。摘要要有落点，说清「给谁/在哪个功能上做什么」，避免「优化了逻辑」这类空话。
- **详细说明**（可选）：需要交代方案、进度或交接细节时，在摘要下方用三级标题分节展开。简单任务只写摘要即可。

任务通过「状态」字段区分

```TASKS.md
# 任务列表

## 增加导出 Excel 功能

- **状态**：待处理

> 在报表页新增「导出」按钮，把当前表格数据下载为 Excel。

## 编辑页新增上传头像能力

- **状态**：待交接
- **交接给**：服务端
- **交接原因**：缺少上传与保存头像的接口能力，需要服务端设计提供

> 编辑页已完成头像上传的前端 UI 展示，具体上传与保存逻辑待接口设计实现后敲定。

### 当前进度

编辑页已新增头像上传入口和图片预览 UI，位于 `EditPage.tsx`，目前仅做本地预览，未接入真实上传。

### 待补充

- 头像上传与保存的接口，需要服务端设计并提供

## 登录页样式调整

- **状态**：已完成

> 在登录页把登录按钮改为品牌蓝，并增大了按钮与输入框的间距，添加了登陆按钮的背景渐变动画，提升登录按钮的视觉效果。

## 导出报表支持自定义列

- **状态**：待验证
- **验证进展**：需要您打开列表页，在导出弹窗中勾选任意列，并且进行导出按钮，检查下载的内容是否一致，如果验证通过，可以告知我已验证

> 报表导出功能已开发完成，支持用户自选导出列，等待验证确认。

### 验证条件

- 报表页「导出」弹窗可勾选任意列组合，至少保留一列
- 导出的 Excel 列顺序与勾选顺序一致，未勾选的列不出现在文件中

## 上传解析支持csv格式文件

- **状态**：已完成
- **验证进展**：用户已手动验证通过，在上传csv文件后，出现进度，表格刷新，展示csv文件内容

> 列表页新增上传 csv 文件解析功能，上传后自动解析并刷新表格展示。

### 验证条件

- 上传 csv 文件后显示上传进度
- 上传完成后表格自动刷新，展示 csv 文件内容

```

**格式区分原则**：
- 一句话能说清的简单任务 → 只写引用块摘要。
- 需要交代方案的复杂或交接任务 → 摘要下用三级标题分节，常用小节：`方案设计`、`当前进度`；开发完成待用户验证的复杂任务，必须补充 `验收进展` 元信息以及 `验收条件` 一节。

**无论摘要还是详细说明，都要「有落点、可追溯」**：具体到页面、模块或文件，写清做了什么、还差什么，而不是「调整了样式」「优化了逻辑」这类模糊描述。

## 元数据字段说明

字段按需使用，缺失直接省略。取值使用固定枚举，便于解析：

| 字段 | 用途 | 取值 |
| --- | --- | --- |
| 状态 | 任务状态（必填） | 待处理 / 待交接 / 待验证 / 已完成 |
| 交接给 | 交接接手方（仅待交接任务） | 角色 |
| 交接原因 | 为什么要交接出去（仅待交接任务） | 一句话说明，如缺少的接口/权限/信息 |
| 验证进展 | 验证的操作方式与结果（待验证/已完成任务） | 待验证时写清用户该如何操作验证；转为已完成后改写为验证结论 |

## 状态流转
一个需求任务的完整链路，通常包含从 **待处理 → 待验证 → 已完成 / 待交接** 三个阶段

定义如下：
已完成：代码改动已落地，且用户可以看到/验证效果
待验证：代码已写，但依赖数据、接口或其他条件，效果需要用户确认
待交接：前端已完成，需要服务端配合才能生效
待处理：还没开始做

对于可以当前项目可以直接闭环完成的任务：比如修改样式、UI修改，通常只需要处理 **待处理 → 待验证 → 已完成** 三个阶段
比如
1. 修改样式，逻辑等简单修改，只需要在代码完成后直接写入 *已完成* 状态即可；
2. UI、逻辑修改中，如果比较包含条件判断、特殊数据mock、特定条件展示这类复杂修改，仅通过修改代码无法确认完成情况，必须经过用户人工验证通过才能完成，需要先提供验证条件并且标记为 *待验证*，「验证进展」写清用户该如何操作验证（例如打开哪个页面、点击哪个按钮、观察什么结果），待用户确认通过后，再把状态改为 *已完成*，并提供「验证进展」。

对于涉及多方的任务：比如涉及服务端数据修改、接口修改，当前项目无法闭环完成时，通常需要处理从 **待处理 → 待交接** 阶段
比如
1. 编辑页新增上传头像能力，前端只能先完成 UI 展示，真正的上传与保存能力需要服务端设计提供，作为前端不应假定或代为设计接口细节（地址、参数、字段等），判定为超出前端可独立完成的范围，标记为 *待交接*，填写「交接给」（服务端）和「交接原因」（缺少上传与保存头像的接口能力），并在「当前进度」「待补充」里写清已完成部分和还欠缺什么能力即可，具体接口方案交由服务端设计；待服务端补齐依赖后，再视情况转回 *待处理* 继续推进，或直接完成前后端对接后转为 *已完成*。


## 维护规则

1. **每次任务完成后维护**：依据用户需求、代码修改和 git diff，更新任务列表。
2. **新增或合并**：完成确定性任务后总结成一条任务；若与已有任务相关，则合并而非重复新增。
3. **摘要必写，详情按需**：每个任务都要有一句话摘要；复杂或需交接的任务再补详细说明。
4. **说明要有落点**：无论摘要还是分节内容，都要写清在哪个页面/模块/文件做了什么，避免空泛描述。
5. **状态流转**：按「状态流转」一节的规则更新任务状态。
6. **字段规范**：字段名和取值严格按上表使用，不要自造，保证可被程序稳定解析。
7. **粒度适中**：动态维护，既不事无巨细，也不遗漏关键任务，核心是保障准确性和可维护性。
8. **有疑问就问**：若对任务归属或交接对象不确定，主动向用户确认意图。

</TASKS.md>

<REVIEW.md>
这一部分描述当前分支已提交和未提交的内容 造成的影响，需要结合修改内容判断。

### 输出位置

变更评估文档报告写入 `.lingchuang/<分支名>/reviews/REVIEW.md`，**按当前 Git 分支名命名文件夹**，最终文件名固定为 `REVIEW.md`，一个分支对应一份报告。分支名应转换成 字母+数字+下划线 三类字符；例如 `feat/add-card` 对应 `.lingchuang/feat_add_card/reviews/REVIEW.md`。

> 如果当前分支已经存在 Review 报告，直接修改文件即可。

### 报告结构

报告顶部是一个 YAML frontmatter，记录 `updateTime`（格式 `YYYY-MM-dd hh:mm`）。

正文由「一级标题 `# 影响列表` + 若干条评估规则」组成。每条规则是一个二级标题的评估维度，结构与任务文档保持一致：

- **二级标题**：规则名称，如 `影响范围`。
- **元数据**：紧跟标题，用 `- **字段名**：值` 的形式列出，既能加粗展示，也能被程序按 `**字段**：内容` 稳定解析。
- **一句话摘要**：紧跟元数据的引用块（`>` 开头），一句话讲清这条规则的评估结论。摘要要有落点，说清「哪个改动 / 涉及哪个功能 / 结论是什么」。
- **详细说明**（可选）：需要展开影响点、待确认项或修复建议时，在摘要下方补充自然段落。结论明确的简单规则只写摘要即可。

### 影响分析规则

- 内置规则：
1. 影响范围，我们面对的是非研发人员，他们无法确认自己的改动是否影响到了线上正在使用的功能，需要评估下当前修改的影响面；

- 自定义规则：
1. 目前暂无，不允许写

> 影响范围目前是必须实现的评估手段，后续可按需扩展新的评估维度（如「兼容性」「性能」等），未涉及的维度直接省略，不要留空标题。

```md
---
updateTime: 2026-09-01 15:30
---
# 影响列表

## 影响范围

- **状态**：需修复

> 千分位改动涉及公共函数 `format`，首页报表也引用了它，会被一并改成千分位展示，需确认首页是否符合预期。

`format` 位于 `utils/format.ts`，除列表页外还被首页报表 `HomeReport.tsx` 调用。导出等其余需求都限定在列表页，影响范围可控，仅首页报表这一处需要人工确认展示合理性。
```

### 元数据字段说明

每条规则的元数据字段固定枚举，便于解析：

| 字段 | 用途 | 取值 |
| --- | --- | --- |
| 状态 | 该维度的评估结论（必填） | 通过 / 需修复 / 严重问题 |

- **通过**：允许上线，无需处理。
- **需修复**：存在需人工确认或修复的点，修复后方可上线。
- **严重问题**：禁止上线，必须先解决。

## 特别注意

- 报告的阅读者是非研发人员，使用清晰具体的业务语言，避免未解释的技术术语。
- 不要为了审计而改动业务源码、需求文档或其他项目文件；只做分析与写审计报告。
- 字段名和状态取值严格按上表使用，不要自造，保证可被程序稳定解析。
