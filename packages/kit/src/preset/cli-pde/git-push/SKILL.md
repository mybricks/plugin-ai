# 推送代码

仅在用户要求提交并推送代码时使用本技能。根据当前对话中的推送诉求，帮用户把内容安全地提交并推送到远端仓库，用户为非研发角色。
> 如果用户没有提及要推送什么内容，则向用户确认需要推送的内容。

你基于任务视角工作的，推送前必须先评估当前改动对应哪些任务、这些任务是否到了可以推送的状态。

注意：不要污染后续动作，后续我没说要推送代码，请不要主动给我推送代码。

## 步骤

### 1. 影响评估
- 结合 git 状态，确认当前推动包含哪些任务的内容。
- 若存在明显不应该提交的文件（如临时文件、密钥、大文件、无关的调试代码），先向用户说明并确认是否排除，不要直接一并提交。
- 注意：项目配置目录中的任务、影响、审计文档属于当前分支的正常产出内容，应当随代码一起提交，不属于「不应该提交的文件」，不要排除它。
- 把评估结论用简单语言告诉用户，例如：「本次推送涉及 3 条任务，其中 1 条还在开发中，2 条待你验证」，让用户在推送前知道这批代码处于什么阶段，用 ask_questions 让用户决策是否真的要推送，推送哪些。

### 2. 提交代码
- 提交前先清理本次推送范围内为「页面展示状态覆盖与交互脚本」临时加入的模拟代码：检查 `window.__LINGSTYLE_DISPLAY_MOCK__` 的引用及「设计态展示覆盖开始/结束」注释，移除展示覆盖逻辑、相关注释和仅为覆盖引入的变量或类型声明，将展示位置恢复为使用原有数据源或计算结果；同时清理配套交互脚本 YAML 中对应的模拟场景，文件仅用于这些场景时才删除整个文件。
- 清理时保留正式功能、样式改动及项目原有的业务 mock、测试数据，不要直接回退整个文件。清理后检查 diff，确认原有展示逻辑已恢复、没有遗留的模拟引用，并执行与改动相关的必要检查，再暂存和提交；已有暂存内容也需同步更新，避免提交清理前的版本。
- 编写清晰的 commit message，概括本次改动做了什么，避免空泛的描述如「更新代码」。

### 3. 推送代码
- 执行 `git push` 推送到当前分支对应的远端。
- 若推送被拒绝（如远端有新提交），如实告知用户冲突原因，不要自行执行可能覆盖他人改动的强制推送（`--force`），除非用户明确要求且清楚风险。

### 4. 收尾汇报
- 向用户汇报：本次推送涉及哪些任务及其状态、提交了哪些改动、commit message 是什么、是否推送成功、推送到了哪个分支。
- 若推送失败，说明失败原因和建议的下一步操作。

## 约束
- 推送前必须先做任务评估，不允许跳过评估直接提交推送。
- 不确定的改动不要擅自提交，需先与用户确认。
