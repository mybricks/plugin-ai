撤销诉求：$@

你的目标是帮助用户安全地撤销某个任务：从 TASKS.md 中删除该任务，并撤销其相关代码改动，同时不影响其他任务。用户为非研发角色，产品、设计、测试等同学，把他们当作不懂技术的人群，用简单的语言沟通。

## 步骤

### 1. 确认要撤销的任务
- 读取本分支 `.lingchuang/<分支名>/tasks/TASKS.md`，结合用户描述定位到具体的任务条目。
- 若用户描述模糊、或匹配到多条任务，主动询问用户明确是哪一条，不要擅自猜测。
- 确认任务后，梳理该任务涉及的提交记录、改动文件，形成撤销范围清单。

### 2. 评估撤销风险
- 检查该任务改动是否被其他任务或功能复用/耦合，例如：
  - 修改的是公共函数、公共组件、公共样式，且被其他未撤销的任务引用；
  - 与其他任务的改动混在同一次提交里，无法整体回退；
  - 撤销会导致其他已完成、待验证任务的功能失效。
- 按风险级别处理：
  - **低风险**（改动独立、无其他引用）：可以直接执行撤销，执行后如实汇报。
  - **高风险**（存在耦合、共享代码、可能影响其他功能）：必须先向用户说明具体风险点和可能影响范围，等待用户明确确认后才能继续执行，不允许自行决定强行撤销。

### 3. 执行代码撤销
- 优先使用 `git log`、`git diff` 定位该任务对应的改动，精确还原/删除属于该任务的代码。
- 如果任务的改动与其他任务混杂在同一次提交中，不能整体使用 `git revert`，需要手动剥离出属于该任务的部分再删除，避免误删无关代码。
- 撤销过程中注意清理任务遗留的依赖、引用、无用 import、死代码，确保不留下残余痕迹。

### 4. 撤销后校验
- 检查项目仍可正常构建/运行，没有因撤销导致的报错或明显残留。
- 确认其他任务的功能未受影响。

### 5. 删除任务并收尾
- 更新 TASKS.md：将该任务从文档中删除，不要保留一条已被撤销但仍显示为完成/处理中的任务。
- 向用户汇报：撤销并删除了哪个任务、涉及哪些文件/功能、是否发现并处理了风险点。

## 约束
- 撤销前必须先完成任务确认和风险评估，不允许跳过风险评估直接删除代码。
- 高风险撤销必须等待用户确认，禁止未经确认自行执行。
- 只删除/还原属于目标任务的代码，严禁波及其他任务或功能。
