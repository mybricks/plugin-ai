推送诉求：$@

你的目标是帮助用户把当前分支的改动安全地提交并推送到远端仓库。用户为非研发角色。

我们是基于任务视角工作的，推送不是单纯的 git 操作，而是任务流转的一个节点：推送前必须先评估当前改动对应哪些任务、这些任务是否到了可以推送的状态。

## 步骤

### 1. 任务评估
- 结合 git 状态，确认当前推动包含哪些任务的内容。
- 若存在明显不应该提交的文件（如临时文件、密钥、大文件、无关的调试代码），先向用户说明并确认是否排除，不要直接一并提交。
- 注意：`.lingchuang` 文件夹是本项目自身的配置目录（任务、影响、审计三类文档），属于当前分支的正常产出内容，应当随代码一起提交，不属于「不应该提交的文件」，不要排除它。
- 把评估结论用简单语言告诉用户，例如：「本次推送涉及 3 条任务，其中 1 条还在开发中，2 条待你验证」，让用户在推送前知道这批代码处于什么阶段，用 ask_question 让用户决策是否真的要推送，推送哪些。

### 2. 提交代码
- 编写清晰的 commit message，概括本次改动做了什么，避免空泛的描述如「更新代码」。

### 3. 推送代码
- 执行 `git push` 推送到当前分支对应的远端。
- 若推送被拒绝（如远端有新提交），如实告知用户冲突原因，不要自行执行可能覆盖他人改动的强制推送（`--force`），除非用户明确要求且清楚风险。

### 4. 收尾汇报
- 向用户汇报：本次推送涉及哪些任务及其状态、提交了哪些改动、commit message 是什么、是否推送成功、推送到了哪个分支。
- 若推送失败，说明失败原因和建议的下一步操作。

## 约束
- 推送前必须先做任务评估，不允许跳过评估直接提交推送。
- 不确定的改动不要擅自提交，需先与用户确认。
