# 领域模块分析

只分析用户指定的项目范围，不修改业务源码。先读取已有 `<documentPath>`，再从页面出发收集事实并归纳模块、领域与业务流程。`docs_understand_domain` 提供结构线索，不负责判定业务边界：

1. 先调用 `docs_understand_domain`（不传 path），获取画布入口列表。结果提示更多条目时，按提示的 offset 和 limit 继续翻页；画布来源不可用或缺失时记录限制，不能视为项目没有页面。
2. 对每个相关画布，将列表中的源码路径作为 path 传入 `docs_understand_domain`，获取该文件的声明。根据画布名称选择对应声明，再将 path 和声明名称作为 symbol 传入，查询它的 JSX 组件引用和调用候选。
3. 沿与页面职责相关的组件和本地导入继续查询文件声明及符号关系；每次仅沿已有代码线索推进。静态引用和调用只是候选，不等于已解析的运行时关系；第三方依赖、动态加载、别名和重导出无法解析时记录限制。
4. 静态事实不足以确认业务含义、路由目标或交互细节时，按需读取对应源码；仅对有依据的页面、模块和流程归纳业务关系。

## 分析顺序与划分规则

### 1. 建立页面清单

先发现页面，再讨论领域和模块。检查应用入口、路由配置、嵌套路由、文件系统路由、菜单配置及已有页面审计文档；结合入口实际指向的组件和源码确认页面。使用 `docs_understand_domain` 从画布入口逐级查看声明、组件引用与调用候选，并沿相关本地导入追踪；仅为补足分析结果按需读取源码及项目文档。它不会直接返回完整页面清单，不能只依赖其 AST 报告。

为每个候选页面整理内部清单：页面名称和用途、真实入口文件、实际路由或菜单入口（能确认才写）、主要用户操作、展示或处理的业务内容、相关请求/跳转和已知流程。对动态路由、插件注册、权限过滤或外部页面无法确认时标记未覆盖；清单不必全部写入 YAML，但须用于后续归纳。分页和多入口要逐一核对，不能把“未找到”当成“不存在”。

页面指用户可进入并完成独立任务的界面，不把按钮、弹窗、表格、普通组件或工具文件单独当作页面；独立弹窗若本身是完整业务入口，可作为相关信息描述，不强行变成页面。参数不同但展示职责相同的路由通常是一类页面；同一个组件承担明显不同的业务任务时可区分页面，具体路由只写有依据的形式。重定向、布局容器和错误兜底不默认作为业务页面，但它们承担清晰业务职责时可以纳入。路由不存在或无法确认时保留可确认的页面，不猜测 route。

页面维度需要在 YAML 的 `edges` 中单独记录实际发生的页面跳转：`type: navigates`，`from` 为来源页面 ID，`to` 为目标页面 ID，`title` 简述触发操作。只在路由、链接、事件处理或其他源码能确认来源、目标与方向时记录；动态目标或外部系统无法确认时记入 diagnostics，不根据相邻路由、菜单排列或业务常识推测。通过 `uses_page` 等实际关系关联模块、领域和流程；流程的步骤可用 `node` 指向已有页面。没有跳转证据的页面仍保留为独立页面节点。

### 2. 从页面归纳业务模块

模块是一组面向用户的、可用一句话说明的业务能力，而不是目录或技术组件。按页面实际业务目标和操作聚合：

- 页面围绕同一个任务或同一组紧密相关的操作，且用户会把它们视为同一能力时，优先合为一个模块。例如订单列表、详情和筛选可组成“订单查询”；不因为 URL 或文件不同就每页建一个模块。
- 业务目标、主要操作或使用场景明显不同，且各自可独立说明时才拆分。例如“订单查询”和“订单创建”可以分开；如果项目很小，两者没有独立的操作或管理边界，也可以归为“订单管理”。不要为了凑层级而拆分单页。
- 先参考用户可见的菜单/页面命名、操作及业务内容，再结合路由、页面跳转、接口和共享数据判断；它们只是线索。共同目录、相同路由前缀或同一个请求库不能单独证明属于同一模块；跨模块跳转也不能单独证明应合并。
- 优先使用项目已有的清晰业务名称。每个模块的 summary 必须说清“帮助谁完成什么”，不得只写“负责相关业务”。不创建单纯对应组件、hooks、utils、技术分层或重复描述的模块。
- 页面可以关联多个确实使用它的模块，不得为了树形结构复制页面；边界暂时无法确定时先放在可解释的较宽模块中，并在 diagnostics 记录待确认事项。

### 3. 从模块归纳业务领域

领域是一组围绕共同业务目标和业务概念的模块。先看模块分别解决什么问题、处理什么业务内容、是否由菜单或项目文档明确组织为同一业务范围，再判断是否合并为领域。

- 业务目标和概念一致、用户能理解为一个完整业务范围时，归为同一领域；只因目录相邻、使用相同技术或出现在同一流程中，不得合并。
- 支付、订单等虽然存在协作，如果职责和主要业务对象明显不同，应保留为独立领域并记录协作关系；跨领域页面或流程可以同时关联多个领域。
- 小型系统只有一个清晰业务范围时允许只有一个领域；如果领域与模块完全重复且无法说明两者不同，不强行构造重复层级。也不要仅依据页面数量规定拆分粒度。
- 每个领域名称和描述要区分其职责与相邻领域；无法判断边界时使用较宽的现有领域，记录不确定之处，不虚构不存在的领域。

### 4. 从页面交互归纳业务流程

流程表示用户或系统完成一个有明确起点和结果的业务过程。先依据页面操作、跳转、请求及可见状态，识别实际发生的步骤和条件，再关联参与的页面、模块或领域。可跨页面、跨模块；“包含”或静态导入不代表先后顺序。没有足够依据时只描述已确认的过程或记录待确认，不能凭业务常识补造分支、失败路径或流程闭环。单页也可以有真实的业务流程，但不要把每个按钮都包装成独立流程。

### 5. 复用并核对

已有页面、模块、领域和流程的稳定 ID、用户修订、名称和归属优先保留；先将本次清单映射到已有节点。只有发现职责或页面归属发生实质变化且有代码依据时，才调整或建议拆分、合并；不因为模型换了称呼就重建节点。部分范围分析时，不删除或覆盖范围外的已有内容。一个页面涉及多个能力时复用同一页面节点，通过关系表达。

生成前逐项自检：已确认的业务页面是否都被表示或说明为何未纳入；每个模块是否能说清能力及其相关页面；领域边界是否能与其他领域区分；流程步骤与分支是否来自实际行为；是否把重复页面、技术目录或共享组件误写为业务实体。业务逻辑或数据支持一个无独立页面的模块或领域时，也可以纳入，但要能说明其业务职责，不能因页面清单缺失就断定其不存在。

文件统计不等于业务覆盖；项目包含不支持的语言、动态注册、分析失败或未检查的范围时说明限制。证据不足时保留已有文档并记录待确认内容，不得编造。确定性校验只能检查协议与引用，不能证明领域划分正确。

## 领域文档

将结果写入 `<documentPath>`，保留已有可信人工修订。面向产品理解，优先描述实体的职责、信息和与其他实体的关系。常见节点包括 domain（业务领域）、module（业务模块或能力）、page（用户操作页面）、flow（业务流程）和 step（流程步骤）；可根据实际项目扩展其他 type。无需凑齐所有类型或强制树形结构；页面和流程可关联多个模块或领域。

YAML 包含 `version: 1`、`nodes` 和 `edges`。节点必须包含稳定的 `id`、`type`、`title`、`summary`；按实际需要补充 `route`、`details`（用户关心的信息，可以是文本或简单列表）、`evidence`（代码定位）和 `status`。关系必须包含 `from`、`to`、`type`；建议用 `title` 和可选 `description` 说明业务含义。`status` 和源码 `evidence` 均非必填，仅在帮助理解或需要溯源时添加；如填写，证据至少包含项目相对 `file`，可补充 `symbol` 和从 1 开始的 `line`。允许复用现有文档中的这些字段，避免删除人工补充的信息。

常用关系类型包括 contains、supports、uses_page、navigates、next、cross_domain，也可按真实业务定义其他类型。`contains` 不表示执行顺序；不要仅按目录命名判断领域或虚构路由、流程与关系。描述不确定的内容时直接在描述或 diagnostics 中说明。

可选 `overview` 提供系统入口信息：`title`、`summary`、`highlights`（字符串数组）、`featuredNodes`（引用已有业务节点 ID）、`featuredFlows`（引用已有 flow 节点 ID）。没有依据时省略这些字段。可选 `flows` 对重要流程记录执行顺序：每项 `id` 必须引用 flow 节点，`steps` 包含流程内唯一 `id`、`title`，可选 `node` 引用已有页面或模块；`transitions` 用 `from`、`to` 引用本流程的步骤 ID，可选 `title`、`description` 描述分支。只有可验证的步骤与分支才写入；不能从包含关系推断流程顺序。支持既有通过 flow → step 的 contains 和 next 边表达流程的文档。

```yaml
version: 1
overview:
  title: 订单系统
  summary: 支持用户创建订单并查看进度。
  featuredNodes: [domain:order]
  featuredFlows: [flow:create]
nodes:
  - id: domain:order
    type: domain
    title: 订单管理
    summary: 管理订单从创建到完成的过程。
  - id: module:create
    type: module
    title: 订单创建
    summary: 为用户提供创建订单的能力。
    details:
      - 填写商品和收货信息
      - 提交订单并查看结果
  - id: page:create
    type: page
    title: 创建订单页
    summary: 用户填写并提交订单的入口。
    route: /orders/create
  - id: flow:create
    type: flow
    title: 创建订单
    summary: 用户填写订单信息并提交。
edges:
  - from: domain:order
    to: module:create
    type: contains
    title: 包含
  - from: module:create
    to: page:create
    type: uses_page
    title: 操作页面
flows:
  - id: flow:create
    steps:
      - id: fill
        title: 填写订单
        node: page:create
      - id: submit
        title: 提交订单
        node: module:create
    transitions:
      - from: fill
        to: submit
        title: 信息有效
diagnostics: []
```
以上仅为格式示例，实际内容必须结合项目事实。写入后调用 `docs_validate_domain`，修复格式、关系引用及已提供的源码定位错误；校验不证明业务描述正确。提示用户在底部「领域」面板查看。
