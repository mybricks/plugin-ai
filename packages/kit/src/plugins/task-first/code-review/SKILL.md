# 代码审查
审查用户指定或者本次修改的代码范围，读取实际 diff 和相关代码修改，并根据规则完成代码审查。

核心流程：了解任务文档以及代码的改动点，分析代码的合理性，最后维护 `overview.yaml` 中的审查信息，维护目标 `change` 的 `checks`。

## 审查范围

- 先读取任务文档，根据任务状态的明确枚举筛选审查范围：
  - 进入审查：`已完成`、`待交接`（本方工作已结束）。
  - 不进入审查：`处理中`、`待验证`（本方工作或验证尚未结束）。
  - 状态缺失、未知或任务无法找到：不进入审查。
  即使用户要求全量审查，也遵循此范围。
- 改动点可能关联多个任务。只要 `tasks` 中至少有一个能在任务文档中找到且状态为 `已完成` 或 `待交接` 的任务，就审查该改动点并更新其 `checks`，即使它同时关联未完成任务；审查范围以符合条件的任务对应的改动为准。没有关联任何符合条件的任务的改动点不进入审查，保留原有 `checks`。
- 没有符合条件的改动点时，说明当前没有可审查的任务改动，不写入审查结论，也不把跳过的任务标记为审查通过。

## 完整示例

```yaml
version: 4
root:
  title: 用户中心
defs:
  - id: avatar
    title: 头像组件
    kind: component
    file: components/Avatar/index.tsx
  - id: upload-avatar
    title: 上传头像接口
    kind: endpoint
    route: POST /api/avatar
  - id: profile-page
    title: 个人资料页
    kind: page
    file: pages/profile/index.tsx
changes:
  - id: C-001
    ref: profile-page
    desc: 个人资料页改用头像组件的默认头像兜底，不再自行拼空白头像地址。
    tasks: [T-001]
    checks:                     # 审查结论
      - title: 头像地址存在第三方来源风险
        severity: critical
        desc: >-
          头像使用外部地址时，打开个人资料页会向第三方发送访问请求。
        action: ai_fix
        next: 限制可使用的头像来源，并在地址不符合要求时显示默认头像。
      - title: 头像资源路径有加载风险
        severity: suggest
        desc: 部署到子路径时头像会加载失败。
        action: dev_collab
        next: 确认部署路径，并调整头像资源的访问方式。
```

| 位置 | 写什么 |
| --- | --- |
| `changes[].checks` | 该改动点的审查结论，每项标题自由命名 |
| `changes[].id` | 独立改动点的稳定 ID；同一对象可关联多个改动点 |
| `defs[]` | 代码对象；改动点通过 `ref` 引用 |

## 字段约束

- `checks` 是可选数组，每项仅允许 `title`、`severity`、`desc`、`action`、`next`，没有 `status`，也没有「通过」项。字段不存在表示未审查或需要重新审查；只有完成审查且没有发现问题时才写 `checks: []`。
  - `title`：非空文本。
  - `severity`：`block` / `critical` / `suggest`，含义见下表。
  - `desc`：非空字符串，用日常语言描述触发场景和用户或业务后果。
  - `action`：必填，取 `ai_fix`（AI 修复）、`prod_decide`（产品决策）或 `dev_collab`（研发协作）。
  - `next`：非空字符串，用一句话写清当前应采取的具体行动。
- `defs` 每项仅允许 `id`、`title`、`kind`、`file`、`symbol`、`route`、`desc`、`parent`；`id` 唯一、非空、无首尾空白且不为 `root`，`kind` 取 `function`、`component`、`page`、`endpoint`、`config`、`data`。
- 不修改 `version`、`root`、已有定义、目标改动点的其他字段或其他 `change`；不要把影响节点写进 `changes`。

## 严重等级

| severity | 界面显示 | 含义 | 使用条件 |
| --- | --- | --- | --- |
| `block` | 高风险 | 必须修，合并前处理 | 代码支持可能造成明显功能失败、数据损坏、安全漏洞 |
| `critical` | 需关注 | 应当修，有异议需讨论 | 代码支持一个具体的缺陷或边界问题，会在真实场景触发，但不至于立即破坏功能 |
| `suggest` | 可改进 | 可考虑的改进或替代方案 | 不影响行为的细节，或当前实现可接受但有更好的实现思路 |

证据不足、路径未被测试覆盖、只有一般性建议时，最高只能判 `suggest`，不得升级为 `critical`。

## 检查怎么写

一个改动点写 0–5 条，只写这次改动独有、代码里有依据的问题。

- 标题一针见血地指出问题所在，写清「哪方面 + 是什么问题」，例如「文件查询性能隐患」「文件判断逻辑有绕过风险」。不要写「分页下推」「正确性」「安全」这类抽象名词、技术术语或分类名。判断标准：没读过代码的同事看到标题就知道哪有风险。
- `desc` 面向产品，用日常语言描述触发场景和具体后果，不展示代码路径、行号、变量、接口字段或技术根因，也不写修复步骤。非页面问题按实际业务或对接场景描述，不虚构用户操作。
- `action` 与 `severity` 分开判断：预期明确且可直接修复时选 `ai_fix`；需要产品确定业务规则时选 `prod_decide`；需要研发确认技术事实或协调依赖时选 `dev_collab`。`next` 写清对应的具体动作和目标，不编造尚未确认的业务规则。
- 不重复罗列影响节点，也不复述改动描述本身。
- 同样的问题不要在多个改动点重复堆砌。
- 先写影响最大的问题；同一等级内按重要性排序。

## 分析步骤

宁缺毋滥：少数有把握的结论，好过一长串猜测。

1. **定位**：读取系统提示词提供的 overview 和任务文档，先按「审查范围」筛选符合条件的任务与改动点，再按改动点 `id` 定位目标 `change`，通过 `ref` 查找其定义；文档不是第 4 版或引用无效时先说明问题，不扩大写入范围。
2. **发现**：读源码、调用方、使用页面或接口实现和相关测试，只保留有代码依据的影响。
3. **验证并过滤**：对每个可疑点回到代码确认，没通过的直接丢弃。
   - 必须能说出具体场景：什么输入或状态会导致什么错误结果。说不出来就不写。
   - 重新核对前提：调用方是否存在、值是否真的可能为空、代码是否真的会被执行到。
   - 区分「本次改动引入」与「原本就有」，后者不写；规则里「不要报告」的内容也不写。
   - 没运行验证过的，`desc` 里不要写成已确认的结论。
4. **写入**：只更新目标改动点的 `checks`。过滤后没有剩余就写 `checks: []`，零发现是合法结果。

## 结束检查

- 每条 `desc` 写清触发场景和后果，不包含代码路径或技术根因；每条 `next` 写清对应的具体下一步。
- 严重等级与真实影响匹配，不把细节问题抬高，证据不足就降级。
- 同一个根因只写一次，不在多个改动点重复。
- 每条 `title`、`desc`、`next` 非空，`severity` 和 `action` 在枚举内，且只使用规定的字段。

## 结束方式

简要说明目标改动点的分析已更新、有无新增定义、`block` / `critical` / `suggest` 各几项。
