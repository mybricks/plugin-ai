# 代码审查
审查用户指定或者本次修改的代码范围，读取实际 diff 和相关代码修改，并根据规则完成代码审查。

核心流程：了解任务文档以及代码的改动点，分析代码的合理性，最后维护 `overview.yaml` 中的审查信息，维护目标 `change` 的 `checks`。

## 审查范围
- 先读取任务文档的各任务状态，确认可审查的具体范围：
  - 进入审查：`已完成`、`待交接`（本方工作已结束）。
  - 不进入审查：`处理中`、`待验证`（本方工作或验证尚未结束）。
  - 状态缺失、未知或任务无法找到：不进入审查。
  即使用户要求全量审查，也遵循此范围。
- 改动点可能关联多个任务。只要 `tasks` 中至少有一个能在任务文档中找到且状态为 `已完成` 或 `待交接` 的任务，就审查该改动点并更新其 `checks`，即使它同时关联未完成任务；审查范围以符合条件的任务对应的改动为准。没有关联任何符合条件的任务的改动点不进入审查，保留原有 `checks`。
- 没有符合条件的改动点时，说明当前没有可审查的任务改动，不写入审查结论，也不把跳过的任务标记为审查通过。

注意：审查动作前务必确认任务文档，因为任务文档的验证情况也可以被用户手动修改。

## 完整示例

```yaml
version: 4
root:
  title: 用户中心
defs:
  - id: avatar
    title: 头像组件
    kind: component
    file: components/Avatar/index.tsx
  - id: upload-avatar
    title: 上传头像接口
    kind: endpoint
    route: POST /api/avatar
  - id: profile-page
    title: 个人资料页
    kind: page
    file: pages/profile/index.tsx
changes:
  - id: C-001
    ref: profile-page
    desc: 个人资料页改用头像组件的默认头像兜底，不再自行拼空白头像地址。
    tasks: [T-001]
    checks:                     # 审查结论
      - title: 头像地址存在第三方来源风险
        severity: critical
        desc: >-
          头像使用外部地址时，打开个人资料页会向第三方发送访问请求。
        action: ai_fix
        next: 限制可使用的头像来源，并在地址不符合要求时显示默认头像。
      - title: 默认头像兜底缺少回归验证
        severity: suggest
        desc: 头像地址失效时的默认头像展示缺少测试，后续修改可能使兜底行为退化。
        action: ai_fix
        next: 补充头像加载失败时显示默认头像的测试。
```

| 位置 | 写什么 |
| --- | --- |
| `changes[].checks` | 该改动点的审查结论，每项标题自由命名 |
| `changes[].id` | 独立改动点的稳定 ID；同一对象可关联多个改动点 |
| `defs[]` | 代码对象；改动点通过 `ref` 引用 |

## 字段约束
- `checks` 是可选数组，分为未审查、审查通过，审查不通过，四类状态。
  - 未审查为 checks 字段不存在，表示未审查或需要重新审查；
  - 已审查，并且没有发现问题为 `checks: []`；
  - 已审查，发现有问题，则补齐问题项，问题项如下；
  每项仅允许以下字段
  - `title`：标题一针见血地指出问题所在，面向非研发同学。
  - `severity`：`block` / `critical` / `suggest`，含义见下表。
  - `desc`：描述触发场景和用户或业务后果。
  - `action`：必填，取 `ai_fix`（AI 修复，预期行为已明确，改动范围可控）、`prod_decide`（产品决策，修复方向取决于尚未确定的业务规则或产品取舍）或 `dev_collab`（研发协作，推进前需要研发确认技术事实、界定影响范围、协调外部依赖或完成修改）。
  - `next`：非空字符串，用一句话写清当前应采取的具体行动。
- `defs` 每项仅允许 `id`、`title`、`kind`、`file`、`symbol`、`route`、`desc`、`parent`；`id` 唯一、非空、无首尾空白且不为 `root`，`kind` 取 `function`、`component`、`page`、`endpoint`、`config`、`data`。

## 严重等级

| severity | 界面显示 | 含义 | 使用条件 |
| --- | --- | --- | --- |
| `block` | 阻塞 | 交付前需处理 | 有证据表明本次交付范围内可触发核心流程无法完成、关键业务结果错误、数据损坏或丢失、越权、敏感信息泄露等严重后果，或已违反项目明确的交付门槛 |
| `critical` | 风险 | 可以继续推进，但需要明确处理或验证条件 | 有具体影响的边界异常、行为口径差异、对接或部署依赖、维护及恢复缺口，或有依据且必须确认的信息缺口；达到阻塞条件时归为 `block` |
| `suggest` | 建议 | 不阻塞审查通过，可结合实际情况处理 | 有具体依据和影响或验证价值的非阻塞建议；不收录纯风格、命名格式偏好或可选优化 |

每项都需要具体依据、适用场景和处理建议。缺少测试只有在能指出具体风险和验证价值时才可作为 `suggest`，不能仅因缺少测试升级为 `critical`；证据不足的猜测和一般性建议不收录。仅有 `suggest` 不导致审查不通过；存在 `block` 或 `critical` 时视为审查不通过。

## 分析步骤

宁缺毋滥：少数有把握的结论，好过一长串猜测。

1. **定位**：读取系统提示词提供的 overview 和任务文档，先按「审查范围」筛选符合条件的任务与改动点，再按改动点 `id` 定位目标 `change`，通过 `ref` 查找其定义
2. **发现**：读源码、调用方、使用页面或接口实现和相关测试，只保留有代码依据的影响。
3. **验证并过滤**：对每个可疑点回到代码确认
  - 依据实际读取的代码、需求、会话记录、接口契约及项目规范判断，不臆造框架、上下游、环境或业务口径
  - 每项发现必须有代码或资料依据、触发条件或适用规范、具体影响和处理建议
  - 只收录本次改动中有依据的问题，包括代码缺陷与维护成本、对接条件及业务规则缺口，不收录正常改动、知会项、纯风格建议、命名格式偏好、可选优化、无证据的性能担忧及无关历史问题
4. **写入**：更新目标改动点的 `checks`

## 结束方式
简要说明目标改动点的分析已更新、有无新增定义、阻塞 / 风险 / 建议各几项。
