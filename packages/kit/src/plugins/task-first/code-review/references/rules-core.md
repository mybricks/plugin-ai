# 内置审查规则

内置的审查思路和规则，作为参考，结合外部注入的审查规则一起作为审查的依据。

## 通过标准

改动让整体代码更好，就可以通过。不因为写法不合个人习惯阻塞，不要求完美。
审查范围为改动点本身及它实际影响到的代码，范围之外原本就有的问题不计入。

## 正确性

> 核心关注：代码在真实输入下是否做对了事。

- 是否符合改动点描述和所属任务，有没有漏掉要求的行为？
- 边界和错误路径是否处理：空值、空集合、失败、超时、半途失败后的残留状态？
- 是否破坏了现有调用方？只修了一个调用方，共享逻辑本身是否仍有问题？
- 高风险逻辑（权限、金额、数据写入、缺陷修复）是否有写错就会失败的测试？
- ...etc

等级参考：功能失败、数据损坏，`block`；有明确触发场景的缺陷，`critical`；缺少测试最多 `suggest`。

## 架构

> 核心关注：代码实现的简洁性、可读性、可维护性。

- 代码是否冗余？代码库中是否已有可复用的实现？是否按周围代码的方式使用？
- 修改边界是否清晰？是否改到了不该改的地方？
- 抽象是否配得上复杂度？有没有为将来预留、实际没人用的东西？
- 复杂度是真的减少了，还是只搬了地方？
- ...etc

等级参考：一般是 `suggest`；已经造成行为错误才按后果升级。

## 性能

> 核心关注：数据量和使用量变大后，是否会明显变慢或出问题。

- 是否存在冗余开销，比如重复执行、重复请求、重复渲染？
- 是否存在逐条查询、无上限的数据拉取？
- 是否存在死循环、内存泄漏？
- ...etc

等级参考：会明显卡死、内存持续增长，`critical`；小重复、可有可无的优化，`suggest`。

## 安全

> 核心关注：不可信的数据、不该暴露的信息，是否被错误对待。

- 不得将敏感数据暴露给用户、日志或提交进 git。
- 外部输入是否在使用前校验？有没有注入或路径绕过的可能？
- 权限校验是否完整，是否只在前端做？
- ...etc

等级参考：可被利用的漏洞、敏感信息外泄，`block`；需要特定条件才能利用，`critical`。

## 不要报告

- 本次改动之前就存在的问题。
- 看起来像缺陷、实际是对的代码。
- lint 与格式化工具能发现的问题。
- 个人风格偏好、模糊的担忧、找不到触发路径的猜测。
- 代码注释里已明确说明范围的有意取舍，除非实际使用量已超出范围。
