# 内置审查规则

内置的审查思路和规则，作为参考，结合外部注入的审查规则一起作为审查的依据。
改动让整体代码更好就可以通过，不因个人习惯阻塞，不要求完美。审查范围为改动点本身及它实际影响到的代码，范围之外原本就有的问题不计入。

逐项检查，不为凑数硬找问题：

| 维度   | 检查内容                                                             |
| ------ | -------------------------------------------------------------------- |
| 正确性 | 分支与边界、并发与重复提交、失败回滚、状态流转、对接契约、数据一致性 |
| 架构   | 规范遵循、统一请求层、改动边界与调用方影响、抽象合理性、依赖合理性   |
| 性能   | 冗余开销、逐条查询、死循环与内存泄漏                                 |
| 安全   | 越权、敏感信息暴露、外部输入校验及可触发场景、环境配置与硬编码       |

## 正确性

> 核心关注：代码在真实输入下是否做对了事。

- 是否符合改动点描述和所属任务？分支、状态流转、核心流程是否完整，有没有漏掉要求的行为？
- 边界和错误路径是否处理：空值、空集合、失败、超时、并发与重复提交、失败回滚、半途失败后的残留状态？
- 数据与状态是否一致：读写一致、缓存失效、本地与远端同步、初始化与销毁？
- 对接契约是否正确：字段名、类型、必填性、错误码、超时重试是否与实际契约对得上？
- 是否破坏了现有调用方？修改或删除对外接口、字段、事件名时，须处理受影响调用方或提供明确的兼容与迁移方案；只修了一个调用方时，共享逻辑本身是否仍有问题？
- 金额、数量、时长等精度计算是否遵循项目既有工具与约定，避免造成精度丢失的浮点运算？
- 高风险逻辑（权限、金额、数据写入、缺陷修复）是否有写错就会失败的测试？

等级参考：功能失败、数据损坏，`block`；有明确触发场景的缺陷，`critical`；缺少测试且有具体风险和验证价值时可判 `suggest`。

## 架构

> 核心关注：代码实现的简洁性、可读性、可维护性。

- 代码是否冗余？是否已有可复用的实现？是否遵循项目既有的开发技术规范和设计规范，按周围代码的方式使用？
- 项目有统一请求层时，是否遵循该层约定，未绕过统一鉴权、错误处理等能力？
- 修改边界是否清晰？改动公共代码或组件时须排查其他调用方，能指出调用方未同步修改而导致功能异常时，构成违规。
- 抽象是否配得上复杂度？有没有为将来预留、实际没人用的东西？复杂度是否真的减少了，还是只搬了地方？
- 新增依赖是否与现有能力重复且无正当用途？仅缺少用途说明不单独构成违规。

等级参考：有具体维护影响或验证价值时可判 `suggest`；已造成行为错误或明确的交付风险时按后果评估 `critical` 或 `block`。

## 性能

> 核心关注：数据量和使用量变大后，是否会明显变慢或出问题。

- 是否存在冗余开销，比如重复执行、重复请求、重复渲染？
- 是否存在逐条查询、无上限的数据拉取？
- 是否存在死循环、内存泄漏？

等级参考：会明显卡死、内存持续增长时按实际影响评估 `critical` 或 `block`；无具体影响的微小重复和可选优化不报告。

## 安全

> 核心关注：不可信的数据、不该暴露的信息，是否被错误对待。

- 敏感信息（手机号、身份证、token、完整地址等）不得未经脱敏写入日志、暴露给用户或提交进 git；须有实际暴露路径才构成违规。
- 外部输入是否按业务和安全边界校验？未校验输入直接拼接进 SQL、命令、路径或 HTML，且有可触发场景时，构成违规。
- 权限校验是否完整，是否只在前端做？
- 接口基址、域名、环境标识等配置须来自环境变量、构建配置或项目既有配置层，不得写死，包括为调试临时写入的数据；能指出写死导致请求打到错误环境或无法切换时，构成违规。

等级参考：可被利用的漏洞、敏感信息外泄，`block`；需要特定条件才能利用，`critical`。

## 不要报告

- 本次改动之前就存在的问题。
- 看起来像缺陷、实际是对的代码。
- lint 与格式化工具能发现的问题。
- 个人风格偏好、模糊的担忧、找不到触发路径的猜测。
- 代码注释里已明确说明范围的有意取舍，除非实际使用量已超出范围。
